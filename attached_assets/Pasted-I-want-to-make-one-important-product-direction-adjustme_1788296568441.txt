I want to make one important product-direction adjustment to the current VOUCH “Earned Autonomy” implementation.

Do NOT rebuild the application and do NOT undo the technical work you just completed.

The current earned-autonomy concept is strong, but I want to sharpen the product so VOUCH is not positioned simply as another “trust score / graduated autonomy” system.

New Core Product Positioning

VOUCH is an adaptive authority engine for AI agents.

Core idea:

VOUCH turns an agent’s verified track record into bounded, revocable authority.

Earned autonomy is the mechanism, not the entire product claim.

The key product question should be:

“Given what this agent is trying to do right now, what has it actually earned the authority to do?”

VOUCH should evaluate authority using the combination of:

Agent history + current evidence + action risk + policy + context + hard safety limits

rather than treating trust as a simple permanent permission or a single score.

Critical Safety Principle

Do NOT implement:

“Approved once = approved forever.”

Do NOT implement:

“Trust increased = this action is permanently authorized.”

Every consequential action must still receive a fresh server-side authorization decision.

A successful verified history can influence the agent’s current authority, but it must never bypass current policy, evidence, risk, or safety constraints.

Think:

Earned authority ≠ permanent permission

Instead:

Earned authority = currently available capability within defined boundaries

Hard policy limits must always override earned trust.

For example:

Low-risk/reversible actions may become autonomous.
Moderate-risk actions may become autonomous only within defined limits.
High-risk, irreversible, destructive, financial, security, or policy-override actions can remain approval-required regardless of trust.

Do not add unnecessary complexity or dozens of new policy types. Preserve the existing architecture and implement this concept cleanly.

The Product Loop

Make the core VOUCH loop:

PROVE → EARN → ACT → VERIFY → ADJUST

The important word is ADJUST.

A verified successful outcome can increase available authority.

A verified failure can reduce available authority.

The next request is evaluated again using the agent’s new state.

Therefore:

History changes authority.
Authority does not eliminate evaluation.

The Signature Demo

The demo should make this behavior unmistakable.

Use one agent and one recognizable class of action.

Show:

1. START

Agent begins at a lower autonomy level.

Example:

T2 — Recommend

The agent can recommend the action but cannot execute it autonomously.

2. PROVE

The agent performs an allowed/reviewed action.

The outcome is successfully verified.

Show:

Verified success

Then:

Trust / reliability improves

and:

T2 → T3

The important message is:

The agent earned additional authority through verified behavior.

3. ACT

The same agent requests the same general class of action again.

This time VOUCH evaluates the current request and allows it because the agent currently has sufficient authority and the action remains within policy boundaries.

Do NOT make this a permanent whitelist.

4. VERIFY FAILURE

Now create a clearly controlled verification failure.

The action itself should not become dangerous; the important event is that the expected outcome does not match the verified outcome.

Show:

Expected ≠ Actual

Then:

Trust decreases

and:

T3 → T2

5. AUTHORITY CHANGES

This is the moment I want the judges to remember.

Have the SAME agent request the SAME GENERAL CLASS OF ACTION again.

VOUCH should now return:

APPROVAL REQUIRED

because the agent’s verified history changed its current authority.

The human approval is the consequence of the loss of authority, not the main feature of the product.

6. RECOVER

After a successful verified action under the lower authority level, demonstrate that authority can be rebuilt.

Show:

Verified success → authority restored

The complete story becomes:

EARN → ACT → VERIFY → LOSE → RECOVER

But make clear that recovery is conditional and bounded.

What Makes VOUCH Different

The UI and copy should NOT repeatedly say:

“VOUCH gives agents trust.”

Instead communicate:

VOUCH determines what an agent has earned the authority to do — right now.

And:

Authority is earned through evidence, constrained by policy, and revoked when behavior proves unreliable.

Another useful explanation:

Trust informs authority. Policy bounds authority. Every action is evaluated again.

These distinctions should appear naturally throughout the product, especially the Homepage, Why VOUCH, How It Works, Control Center, Judges, and Architecture pages.
